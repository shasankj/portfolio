decisions:
  - decision: "Safety enforced in code around the model, not only in the prompt"
    why: "Prompts are requests; guards are not. Input guard, fencing, a strict prompt and an output verifier give four independent layers."
    alternative: "A single strong system prompt and trusting the model to follow it."
  - decision: "PostgreSQL with pgvector for vectors and relational data"
    why: "One transactional store gives SQL joins, vectors, full-text search, audit and backups, with one system to secure."
    alternative: "A dedicated vector database (Pinecone, Qdrant, Weaviate); not built for billions of vectors, but unnecessary at this scale."
  - decision: "Direct SQL for retrieval (distance, tsvector, RRF, filters)"
    why: "The LangChain wrapper could not express hybrid fusion, joins to a sources table, iterative scan or the relevance gate."
    alternative: "The LangChain PGVector wrapper from the original spec."
  - decision: "Four fixed MCP tools instead of a free-form SQL tool"
    why: "The model never writes SQL and never even sees a member_id parameter, so the attack surface is tiny and identity comes from the session."
    alternative: "Text-to-SQL, which is more flexible but lets the model choose whose data to read."
  - decision: "Stream progress, not tokens"
    why: "Unverified text must never reach the user, so the UI shows a live pipeline timeline and the verified answer arrives last."
    alternative: "Token streaming with a typewriter effect, plus post-hoc verification."
  - decision: "Local embeddings (bge-base-en-v1.5, 768 dimensions)"
    why: "No per-call cost, health text stays on the server, and retrieval quality is strong."
    alternative: "A hosted embeddings API, or the smaller 384-dimension model."

People ask insurance and pharmacy questions where a confident wrong answer does real harm: what a plan covers, what a drug's label says, what their own copay is. A plain chatbot improvises. I wanted an assistant that behaves like a careful pharmacist's aide: it cites every factual sentence, admits when it has no evidence, refuses medical advice, and can never be talked into reading someone else's records.

The interesting engineering is the trust boundary. The model is wrapped by layers I can test and measure, so safety does not depend on the model behaving well. Patient identity is decided by a signed cookie, retrieval is split into two enforced modes (coverage questions search only Medicare documents, drug questions search only the named drug's FDA label), and every draft must pass a verifier before the user sees it.

All patients are synthetic and the sign-in is simulated. It is a portfolio project, not a medical device.
