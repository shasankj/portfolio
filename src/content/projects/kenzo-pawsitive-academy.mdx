  - decision: "Exclusion constraints in Postgres for rooms and teachers"
    why: "The database itself rejects overlapping classes, so the invariant holds no matter which code path writes."
    alternative: "Overlap checks in application code."
  - decision: "Events through SNS and SQS with a dead-letter queue"
    why: "Email failures cannot slow or break a booking, retries are automatic, and the sender needs no database access."

A dog training academy needs more than a list of classes. Pups, or their owners, should choose a real seat on a seat map, trainers should publish and cancel their own classes, and an admin, the Head Dog, should approve new accounts and manage everything else. The hard part is correctness under concurrency: two people tapping the same seat at the same moment must produce exactly one booking and one clear error, and a cancelled class must free its room and notify exactly the right people.

I used the project to practise a real serverless backend end to end: one Lambda per endpoint, Postgres for relational truth, DynamoDB for the contested resource, and an event pipeline so slow side effects like email never sit in the request path.
