Two people tap seat B3 at the same moment. Exactly one should win, and the other should get a clear message, not a silent double booking.

## The tempting approach

Read the seat, see that it is free, write it. Between the read and the write, someone else can do the same. That is a race, and it only shows up under load.

## What I did instead

The seat lives in DynamoDB, and booking is one `TransactWriteCommand` with two puts:

1. the seat item, keyed by class and seat, with `attribute_not_exists(sk)`
2. a marker item for the student in that class, with the same condition

If either condition fails, neither write happens. A taken seat fails the first condition and the user sees "That seat was just taken". A student who already has a seat fails the second and sees "already booked".

## Where Postgres fits

Postgres still answers the relational questions in one query: does the class exist, is it scheduled, has it started, is the student account active. DynamoDB owns only the contested resource, the seat.
